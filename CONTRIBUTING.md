## Кодекс поведения

Этот проект принимает [Кодекс поведения](CODE_OF_CONDUCT.md). Участвуя в проекте, вы соглашаетесь соблюдать его положения. Сообщайте о неприемлемом поведении лидерам сообщества.

## Как я могу внести вклад?

### Сообщение об ошибках

Если вы обнаружили ошибку, создайте issue с меткой `bug`. Включите следующую информацию:

- **Краткое описание** проблемы
- **Шаги для воспроизведения**
- **Ожидаемое поведение**
- **Фактическое поведение**
- **Версия** приложения/библиотеки
- **Окружение** (ОС, версия Rust, версии зависимостей)
- **Пример кода** или скриншоты, если применимо

### Предложения функций

Для предложений новых функций создайте issue с меткой `enhancement`. Опишите:

- **Какую проблему** решает функция
- **Предлагаемое решение**
- **Альтернативные решения**, которые вы рассмотрели
- **Дополнительный контекст**

### Внесение кода

1. **Форкните** репозиторий
2. **Создайте ветку** для вашей функции или исправления:
   ```bash
   git checkout -b feature/название-функции
   # или для исправлений:
   git checkout -b fix/описание-исправления
   ```
3. **Внесите изменения** в код
4. **Закоммитьте** изменения следуя [правилам коммитов](#коммиты)
5. **Запушьте** ветку в ваш форк:
   ```bash
   git push origin feature/название-функции
   ```
6. **Откройте Pull Request** в основной репозиторий

## Требования к коду

### Rust (Backend)

- **Rust 1.70+**
- Код должен компилироваться без предупреждений
- Все публичные функции должны иметь документацию
- Избегайте `unwrap()` в продакшен-коде, используйте корректную обработку ошибок
- Следуйте [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/)

### Frontend (HTML/CSS/JS)

- Используйте современные стандарты ES6+
- Избегайте глобальных переменных
- Соблюдайте семантику HTML5
- CSS должен быть адаптивным и доступным

## Стиль кода

### Rust

Проект использует стандартные соглашения Rust:

- Имена типов: `PascalCase`
- Имена функций и переменных: `snake_case`
- Имена констант: `SCREAMING_SNAKE_CASE`
- Отступы: 4 пробела
- Максимальная длина строки: 100 символов

Для автоматического форматирования используйте:
```bash
cargo fmt
```

Для проверки стиля:
```bash
cargo clippy
```

### JavaScript

- Используйте `const` и `let`, избегайте `var`
- Стрелочные функции для callback'ов
- Шаблонные строки для интерполяции
- Отступы: 2 пробела

## Коммиты

Проект следует соглашениям [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <краткое описание>

<опциональное тело>
```

### Типы коммитов:

- `feat` — новая функция
- `fix` — исправление ошибки
- `docs` — изменения в документации
- `style` — форматирование, отступы (без изменений логики)
- `refactor` — рефакторинг кода (без новых функций и исправлений)
- `test` — добавление или изменение тестов
- `chore` — изменения в сборке, зависимостях, конфигурации

### Примеры:

```
feat(parser): добавить поддержку указателей на функции

fix(generator): исправить генерацию циклов for с вложенными условиями

docs(readme): обновить секцию установки для macOS

refactor(ast): упростить обработку вложенных структур
```

## Pull Requests

### Перед отправкой PR убедитесь:

- [ ] Код компилируется без ошибок и предупреждений
- [ ] Все тесты проходят (`cargo test`)
- [ ] Код отформатирован (`cargo fmt`)
- [ ] Пройдена проверка `cargo clippy`
- [ ] Добавлены тесты для новых функций
- [ ] Обновлена документация при необходимости
- [ ] Коммиты следуют [Conventional Commits](#коммиты)

### Процесс ревью:

1. Все PR должны быть проверены как минимум одним мейнтейнером
2. После одобрения PR будет объединён с основной веткой
3. При необходимости внесённые изменения будут запрошены через комментарии

### Шаблон PR:

```markdown
## Описание
Краткое описание изменений

## Тип изменений
- [ ] Новая функция
- [ ] Исправление ошибки
- [ ] Рефакторинг
- [ ] Документация
- [ ] Тесты

## Связанные issue
Closes #<номер>

## Чеклист
- [ ] Код компилируется без предупреждений
- [ ] Все тесты проходят
- [ ] Добавлены тесты (если применимо)
- [ ] Обновлена документация (если применимо)
```

## Тестирование

### Запуск тестов

```bash
# Все тесты
cargo test

# Тесты конкретного модуля
cargo test --lib parsers

# Тесты с выводом
cargo test -- --nocapture
```

### Написание тестов

- Unit-тесты должны быть в том же файле, что и тестируемый код (модуль `#[cfg(test)]`)
- Интеграционные тесты размещаются в `src-tauri/tests/`
- Тесты должны быть независимыми и воспроизводимыми
- Используйте осмысленные имена для тестовых функций

## Документация

- Обновляйте `README.md` при изменении функциональности
- Добавляйте примеры использования для новых функций
- Документируйте публичные API через rustdoc комментарии:
  ```rust
  /// Краткое описание функции
  ///
  /// Подробное описание с примерами использования
  ///
  /// # Примеры
  ///
  /// ```
  /// let result = some_function();
  /// ```
  pub fn some_function() -> Result<()> {
      // ...
  }
  ```
